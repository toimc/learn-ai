# 多 agent 编排演示示例 — 设计规格

- 日期：2026-08-29
- 状态：设计经用户分节确认（架构/数据流/错误与测试三节）
- 分支：`feat/multi-agent-demo`（worktree）
- 定位：纯演示性质的通用多 agent 示例，供 playground 演示；覆盖委托/并行/流水线三种协作形态；全部代码进 dev-server 私有包（+playground 演示层），不动发布包

## 1. 背景与目标

16-03 笔记讲了 Explorer/Executor 委托模式与「task 工具是普通工具」，但代码未落地；现有 `chat-agent`/`docs-agent` 是平级独立 agent，无协作。本示例补上这个空洞：

- 同一预置问题，三种编排形态（委托/并行/流水线）行为**可复现、可对比**——形态是代码不是提示词
- 与现有 wire 协议零改动：协作过程全部经 `tool_call`/`tool_result` 帧呈现
- 无 API Key 时 mock 剧本回放，协作卡片完整可见
- 呼应 16-03：按角色选模型（可选 env）、错误字符串返回不打断父链路、父 Agent 独占用户对话

## 2. 架构

```
playground 演示页 MultiAgentDemo.vue
  形态切换（委托/并行/流水线）+ 预置示例问题
  发送时 prepend system 指令「本次使用 X 模式编排任务」
  CollaborationCard（orchestrate 工具定制渲染）
        │ SSE（现有 sse-adapter，零协议改动）
        ▼
dev-server orchestrator-agent（注册进网关 → 模型下拉可见；Studio 可调试）
  orchestrate(pattern, task) 工具 —— LLM 只做路由与汇报
    delegate ：researcher → writer（两步委托）
    parallel ：researcher×3 并行（allSettled）→ 结果并列呈现
    pipeline ：检索 → 起草 → 审查；审查不过打回重写 ≤1 次
  内部子 agent（new Agent；不进网关注册表；进 Studio 便于单独调提示词）
    researcher-agent：search_docs 工具，只读检索
    writer-agent：无工具，基于检索结果起草
    reviewer-agent：无工具，对照检索结果审查草稿
mock 剧本：按「委托/并行/流水线」关键字分发三套回放
```

### 关键决策

1. **编排即代码**：三种形态是 `patterns.ts` 纯函数（输入子 agent 调用接口、输出 `OrchestrationResult`），不是提示词
2. **注册表语义不变**：`buildAgentDefinitions` 只 +1 行（orchestrator）；子 agent 走独立 `teamDefinitions(env)`，仅 Studio 宿主组装 `[...buildAgentDefinitions(env), ...teamDefinitions(env)]`。网关模型下拉只有 orchestrator 一个新入口
3. **按角色选模型（可选 env）**：`MASTRA_SUB_MODEL`——配置则 researcher 用它（高频便宜活），writer/reviewer 用 `MASTRA_MODEL`；不配全用主模型。`.env.example` 补充说明
4. **不动发布包**：无 `@toimc/server` 类型变更（子 agent 不加 internal 标志位）

## 3. 跨 lane 契约（所有实现必须与本节完全一致）

### 3.1 标识符

- 网关 agent id：`orchestrator-agent`，name「多 Agent 编排助手」
- 子 agent id：`researcher-agent` / `writer-agent` / `reviewer-agent`，name「检索员」「起草员」「审查员」
- 工具：Mastra tool key `orchestrateTool`，**工具名（wire 上 toolName）`orchestrate`**

### 3.2 orchestrate 工具 zod schema

```ts
{
  pattern: z.enum(['delegate', 'parallel', 'pipeline']),
  task: z.string().describe('要编排完成的用户任务描述'),
}
```

工具 description 写明三种 pattern 各自何时使用、NOT TO USE 场景（16-03：工具描述是模型的路由文档）。

### 3.3 OrchestrationResult（tool_result 返回值，卡片数据源）

```ts
interface StageResult {
  role: 'researcher' | 'writer' | 'reviewer'
  agentId: string          // 'researcher-agent' 等
  status: 'ok' | 'error'
  durationMs: number
  model: string            // 该阶段实际使用的模型标识
  usage?: { inputTokens: number; outputTokens: number }
  output?: string          // 该阶段产出，卡片内折叠展示；error 时为错误摘要
  meta?: { retried?: boolean; verdict?: 'pass' | 'revise' }
}

interface OrchestrationResult {
  pattern: 'delegate' | 'parallel' | 'pipeline'
  task: string
  stages: StageResult[]
  finalDraft: string       // 流水线=终稿；委托=writer 稿；并行=空串（由 orchestrator 综合）
}
```

- `retried: true` 标记打回后重写的那次 writer 执行；`verdict` 取最终审查结论
- 并行形态 `finalDraft` 为空串：三路检索结果并列在 stages 里，综合汇报交给 orchestrator LLM

### 3.4 形态指令协议（演示页 ↔ orchestrator）

演示页发送前 prepend 一条 system 消息，**精确字符串**：

- 委托：`本次使用委托模式编排任务`
- 并行：`本次使用并行模式编排任务`
- 流水线：`本次使用流水线模式编排任务`

orchestrator instructions 必须写明：见到该指令时以对应 pattern 调用 orchestrate 工具；未见指令时自行判断最合适的 pattern。

### 3.5 mock 剧本关键字（scenarios.ts 分发）

- `/委托|delegate/i` → delegate 剧本
- `/并行|parallel/i` → parallel 剧本
- `/流水线|pipeline/i` → pipeline 剧本
- 预置问题文案必须包含对应关键字，保证 mock 模式分发正确

### 3.6 预置示例问题（演示页，三形态共用一套）

1. `InputArea 的 Enter 键行为是什么？Shift+Enter 又是什么？`（含「委托」前置指令时走两步委托）
2. `主题定制有哪些方式？CSS 变量覆盖和预设怎么选？`
3. `多会话管理的数据存在哪里？怎么持久化？`

发送规则（mock 分发依赖）：mock 场景 match 的输入是**用户消息文本**，system 指令消息不参与 match，因此演示页在预置问题原文前拼接形态词作为发送文本——如 `【流水线】InputArea 的 Enter 键行为是什么？…`。真实模式下 orchestrator 同时收到 system 指令与该前缀，二者口径一致无冲突。

## 5. 行为规格

### 5.1 三种编排语义

- **delegate**：researcher 检索（prompt=任务）→ writer 起草（prompt=任务+检索输出）。stages 顺序 [researcher, writer]
- **parallel**：3 个 researcher 并行，prompt 分别带角度提示（「组件用法」「配置与主题」「集成与数据」）；`Promise.allSettled`，单路失败不影响其他路。stages 3 项并列
- **pipeline**：researcher → writer（起草）→ reviewer（对照检索结果审查，输出 verdict：`pass`/`revise` + 意见）。`revise` 则 writer 重写一次（prompt 附审查意见，`retried: true`），重写后**不再复审**，`verdict` 保留首次审查结论并附说明。stages 顺序 [researcher, writer, (reviewer, writer-retry?)]

### 5.2 orchestrator instructions 要点

- 人格：多 agent 编排助手；自己不直接检索/起草，一律经 orchestrate 工具
- 指令协议（3.4）与工具 pattern 一一对应
- 汇报规范：基于 OrchestrationResult 汇报——流水线呈现 finalDraft 与审查结论；并行综合三路检索结果；委托呈现 executor 稿；某路/某阶段 error 时如实说明缺了什么，不编造
- 不重写子 agent 产出（呈现而非改写）

### 5.3 mock 剧本

三套剧本各含：`thinking`（编排意图简述）→ `tool_call`（orchestrate，参数含 pattern 与 task）→ `tool_result`（手写 OrchestrationResult 字面量，含 stages/耗时/usage/meta）→ `text`（汇报正文）→ `done`。delay 节奏参照现有 toolScript 手感（tool_call 前 ~500ms，tool_result 前 ~900ms）。

## 6. 错误处理

| 故障点 | 行为 |
|---|---|
| 某路 researcher 失败（并行） | 该 stage `status:'error'`，其余路照常 |
| researcher 失败（委托/流水线） | 中止后续阶段，返回已完成 stages + 错误 stage；finalDraft 空串 |
| writer/reviewer 失败 | 保留已完成阶段；finalDraft 空串并在结果中可见错误 stage |
| 二次审查仍不过 / 重写后 | 不再循环；verdict 如实呈现 |
| orchestrate 工具整体异常 | catch 后以错误字符串作为工具返回值（不抛异常，不打断父链路），orchestrator 转述 |
| 无 key 真实模式 | 现有 env 门控：orchestrator 不注册，请求落 mock 剧本 |

## 7. 测试策略（红灯先行）

## 9. 明确不做（YAGNI）

- 不做动态路由/递归委托（子 agent 不能再委派）
- 不做子 agent 中间过程的实时流式（受 MastraAdapter 丢弃 tool-output 限制；卡片在 tool_result 时整体呈现，属已知可接受限制）
- 不做 token 成本估算展示、不做协作关系图可视化
- 不改 `@toimc/server` / `@toimc/agents` / `@toimc/core` 任何发布代码
