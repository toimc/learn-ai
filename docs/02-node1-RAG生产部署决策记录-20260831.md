## 2. 决策链：为什么是 Ollama 而不是 TEI

笔记 17-04 推荐推理服务选 TEI CPU，现场落选。完整因果链：

**第一环：同模型原则锁死 bge-m3（不可绕过）**

本地向量库（473 chunks）用 **Ollama bge-m3**（1024 维）生成。RAG 铁律：入库与查询必须同一 embedding 模型，否则向量空间不可比、检索直接失效。因此服务器推理服务必须能跑 bge-m3——笔记里 TEI 的低配方案（bge-small，2C2G）从一开始就不可选。

**第二环：TEI 跑 bge-m3 的内存账算不过来**

TEI 不走 GGUF 量化路线，bge-m3（567M 参数）在它手上是 f32 权重 + 运行时开销：

- 纯权重 ~2.2GB，全栈峰值 4G 起步（笔记 17-04 自己写明「bge-m3 则 4G 起步」）
- 机器共 3.6G 内存，还需养系统 + Docker + nginx → 实测 OOM

**第三环：Ollama 不只是退而求其次，还白赚一个正确性收益**

建库侧 Ollama bge-m3，查询侧同 Ollama bge-m3——**同模型、同实现、同量化**，语义空间零偏差。若本地 Ollama（q8）建库、服务器 TEI（f32）查询，虽是「同一个模型」，量化差异理论上引入细微向量偏移。同实现最稳。

> 笔记并未被违反：17-04 的推荐带条件分支（TEI bge-small → 2C2G；TEI bge-m3 → 4G 起步），现场 3.6G + 锁死 bge-m3 正好落进预判的「不适用」分支；Ollama 本就是笔记列出的四个推理选项（TEI / infinity / Ollama / transformers.js）之一。

## 3. infinity 为什么也不行

| 方案 | 内存账 | 实现偏差 |
|---|---|---|
| TEI CPU | f32 权重 ~2.2G + 运行时，峰值 4G 起 | ❌ 与 Ollama 建库不同实现 |
| infinity（torch 引擎） | PyTorch 运行时税 ~500M baseline + f32 权重 ≈ 2.6G+，比 TEI 还不省 | ❌ 同上 |
| infinity（ctranslate2 int8） | 理论 ~1.5-2G，但 bge-m3 架构（XLM-R + 自定义 pooling）在 CTranslate2 上支持存疑，需验证 | ❌ 同上 |
| Ollama | GGUF q8 常驻 1.76G，实测稳跑 | ✅ 与建库同实现零偏差 |

infinity 的真正卖点是**一个服务同时挂 embedding + rerank**——当前架构未上 rerank（17-04 中为可选进阶），优势用不上；其 Python 服务的 PyTorch 进程 baseline 内存税躲不掉，内存账不比 TEI 好，还背同样的实现偏差问题。

## 4. 为什么不换小模型

「bge-m3 太大就换 bge-small」技术上完全可行（笔记 17-04 也写了 bge-small 2C2G 的合法分支），但被两个事实封死：

**质量税正好打在要害上**

闭环验证的案例：「聊天气泡怎么用」→ `message-bubble.md`、「切换暗色主题」→ `theming.md`——**中文口语查询命中英文文件名文档**，正是 bge-m3 多语言对齐（100+ 语言共享语义空间）在干活。换 bge-small-zh（~24M，中文为主）对英文文件名、代码术语的表征弱得多，跨语言检索明显退化——等于把 16-02 同义词表想解决的那个问题又请回来一半。

**关键反转：「bge-m3 太大」这个前提本身已被消解**

> TEI 跑不动 bge-m3 ≠ 这台机器跑不动 bge-m3

Ollama 的 q8 量化让 567M 的 bge-m3 以 1.76G 常驻跑在 3.6G 机器上且留有余量，检索质量基本无损（q8 对余弦排序的影响不可测）。换 bge-small 省下 ~1.5G 内存——现状内存够用、磁盘余 45G，**这 1.5G 没有买家**；代价却是实打实的：换维度（1024→512）= LibSQLVector 换表重建 + 本地重新嵌入全量 47 篇 + 跨语言质量降级。

### 决策框架：先量化，后降级

优化资源占用的优先级：

1. **先试量化**（同模型降到能跑：f32 → q8 → q4），质量损失递增但 q8 基本无损
2. **量化也跑不动才降级模型**——降级是「拿检索质量换资源」的最后手段，不是第一反应

什么时候真的该换小模型：

- 内存 <2G 可用——连 q8 的 bge-m3 都撑不住
- 极端延迟要求——q8 CPU 上 bge-m3 单 query 数百 ms，bge-small 数十 ms
- 高吞吐——查询量大到 CPU 成瓶颈（几十在线用户无压力，见 17-04）
