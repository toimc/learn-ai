## 架构与代码健康发现

### P0（架构红线/安全/正确性风险）

- **`@toimc/core` 发布产物内联了完整 Vue 运行时，且 `vue` 在 package.json 中零声明** — 证据：`packages/core/dist/index.mjs:1-2` 起即 `//#region .../@vue+shared@3.5.41/...`，region 标记显示 `@vue/shared`、`@vue/reactivity`、`@vue/runtime-core`、`vue@3.5.41` 全部内联（60KB ESM / 44KB CJS，零 `import 'vue'` 语句）；根因在 `packages/core/vite.config.ts:15`（`external: []`）+ `packages/core/package.json`（dependencies/peerDependencies 均为空）；源头是 `packages/core/src/composables/index.ts:1`（`import { reactive } from 'vue'`）。为什么是问题：npm 上已发布 `@toimc/core@0.0.1`；宿主同时装 `@toimc/core`（自带私有 Vue）与真实 Vue 渲染 `@toimc/vue` 时是**双 Vue 实例**——useChat 的 reactive 状态由私有副本插桩，宿主组件渲染时不会建立依赖追踪，**流式更新静默失效**。同时直接违反 core 零外部依赖红线（frontend-typescript §7）与根 CLAUDE.md「core 无外部依赖，纯 TypeScript」描述。建议动作：package.json 加 `"peerDependencies": { "vue": "^3.5.0" }` + `external: ['vue']`，并同步修正 CLAUDE.md 的「纯 TS」表述为「对宿主 Vue 的 peer 依赖」。
- **测试体系结构性测不到 dist——发布物回归零防线（上述 P0 的根因）** — 证据：`vitest.config.ts:10-12` 与 `packages/docs/.vitepress/config.ts:84-87` 都把 `@toimc/*` alias 到 **src**；全部内部消费（测试/文档站/type-check）都走源码，dist 只被 npm 外部消费者使用。为什么是问题：vite external 配置漂移、依赖误打包（下条 vue-i18n 即同类）永远不会在仓库内暴露；14 章的「安装后验证」只单独 import 各包（自带 Vue 可自满足），测不出双实例反应性断裂。建议动作：加一个 dist 冒烟测试（临时目录 `npm pack` 安装全部 5 包，断言 `@toimc/core` 产物 `import 'vue'` 且与宿主 vue 单例共享 reactive 追踪）。

- **dev-server providers 路由安全簇（node1 公网部署时为实际暴露面）** — 证据：① `packages/server/src/create-gateway.ts:37-38` bearerAuth 只挂 `/chat` 与 `/models`，`app.ts:120` 挂载的 `/api/providers` POST/PUT 完全无鉴权（设了 DEV_SERVER_TOKEN 也拦不住注册/覆盖 provider）；② `packages/dev-server/src/routes/providers.ts:46` `process.env.ANTHROPIC_API_KEY = payload.apiKey`——进程级全局覆写，多访客注册 Anthropic provider 互相顶 key，属正确性+安全双缺陷；③ `packages/dev-server/src/app.ts:88` apiKey 明文落盘锚定 `process.cwd()/.temp/providers.json`，与 `paths.ts` 的包根锚定（专为抗 cwd 漂移设计）不一致，密钥文件位置不可预测；④ `packages/dev-server/src/agents/model-config.ts:19-24` `normalizeEndpointUrl` 不校验协议与主机（SSRF 中继面）。建议：auth 扩到全部写路由；Anthropic key 走 per-agent env 注入而非 process.env；persist 路径改用 `tempFilePath()`。

### daydayup 设计建议

定位：夜间自评审 + 知识沉淀循环，产物落 `docs/daydayup/`（目录现为新建）。五条具体建议：

1. **审查环节扩为「代码 + 结构 + 知识」三轴**。代码轴之外固定四步，全部可脚本化起步：
   - 结构保鲜校验（本次审计的主体，纯脚本即可）：包清单 vs `packages/`、AGENTS.md skills 清单 vs `git ls-files .claude/skills/`、全部引用路径存在性、CI paths vs 实际文件、覆盖率文案 vs vitest.config.ts。
   - 规则漂移对账：`diff` 双轨同名文件（git-flow-worktree、dowhat、dependency-updater）；规则承诺 vs 配置现实（如「core 90/vue 70 门禁」实际不存在）。
   - memory 对账与升级候选：扫 memory 索引，标出「描述与现状不符」（如 vitest-package-scope-quirk 的 include 已改）与「满足三标准（项目特有/高频/可执行）但 rules 未覆盖」的条目，产出升级建议 diff。
   - 上期行动项回顾：读上一份日报的行动项，逐条标 done / 逾期 / 放弃，逾期项带原因。
2. **两档运行模式，这是防烧 token 的核心**。轻量档（纯脚本：断链/清单/漂移/git 变更面探测，零或单次 LLM 调用）与完整档（多 agent 并行审查）。定时触发（cron/loop）**只跑轻量档**，脚本发现异常才升级到完整档并通知用户；手动 `/daydayup` 默认完整档。参考用户全局规则里 2026-06-22 auto-pilot 789 次空转事故的边界：「该干的活别以 token 为由缩，无意义的空转一秒都别跑」——两档制正是把这个边界机制化。
3. **增量与短路收场**。完整档先跑变更面探测（自上期日报记录的 HEAD 以来的 `git diff --stat`），某轴无变更就在日报写「本期无变更，未审查」直接跳过该轴，不重扫全库；全轴零发现时输出固定「无新发现」模板（含上期回顾与指纹），不凑数、不硬挖。每个并行 agent 设硬预算（最大轮次/token），超限即中止并在报告注明「预算耗尽于第 N 步」。
4. **复核闸门 + 人工闸门双层**。多 agent 的候选发现必须经主线对抗复核（去重、降级、要求落到具体文件与行号证据——本次审计的纪律直接复用）才能进日报；其中 memory→rules 升级、AGENTS.md 修正这类「改行为契约」的产出，daydayup 只给建议 diff，**不自动落盘**，等用户确认后合入（规则是所有 agent 的行为契约，自动化改动风险不对称）。
5. **日报契约与幂等**。固定结构：发现（带文件证据）/ 行动项（带 owner + 验证命令）/ 记忆候选 / 规则变更建议 / 上期回顾。行动项的「验证命令」让下一期回顾可机器判定 done。同日重跑幂等：给每条发现算指纹（文件路径 + 结论哈希），重复发现不重复报告；日报头部记录当期 HEAD，作为下期增量基线。
