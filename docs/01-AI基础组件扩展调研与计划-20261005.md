## 2. 协议决策建议：保留现有 Message/StreamChunk + 加法式渐进增强

### 2.1 决策

**建议：不做 parts 模型迁移，走「可选字段加法 + 状态机扩宽 + 逃生舱约定」三件套。** 总架构师需对本节 2.4 的三个子项拍板。

### 2.2 论证

**（1）破坏面量化，大改不划算。** `Message`/`StreamChunk` 贯穿四层：core types + useChat 消费、vue 全部展示组件 props、dev-server SSE 产出端（agents/mastra 网关）、700+ 测试与 24 页组件文档。改成 UIMessage parts 数组等于 core/vue/dev-server 三包同步重写 + 对宿主 breaking change，v0.x 阶段（deprecated 组件尚未移除）不可承受。

**（2）语义等价：现有协议就是 parts 的扁平化投影。** 对照 AI SDK 11 种 part：`attachments` ≈ FileUIPart、`toolCalls` ≈ ToolUIPart、`thinking` ≈ ReasoningUIPart、`comparison` ≈ DataUIPart、`metadata: Record<string, unknown>` ≈ 自定义 data 通道。parts 的核心增量价值在「双向转换」（`convertToModelMessages`，数据层 SDK 需要）；本项目是**渲染优先的组件库**，宿主拿组件拼 UI，不需要双向转换，扁平字段的开发体验反而更好（`message.toolCalls` 直接 v-for）。

**（3）真正的能力缺口全部可以用加法补齐，不动骨架：**

| parts 模型能力 | 本项目加法路径 | 兼容性 |
|---|---|---|
| SourceUrl/SourceDocument part | `Message.sources?: MessageSource[]` 新可选字段 | 纯加法 |
| ReasoningUIPart 多步 | `ThinkingInfo.steps?: ThinkingStep[]` 新可选字段 | 纯加法 |
| 工具 7 态状态机 | `ToolCallInfo.status` 枚举扩宽（见 2.3） | union 扩宽是源兼容（旧值仍合法），穷举 switch 处补 default |
| step-start 边界 | `ThinkingStep` 的 status 时间线天然表达 | 无需单独 part |

**（4）生态互通留桥（P2，不在本期）。** 可选提供 `toUIMessageParts(message): UIMessagePart[]` 单向适配函数给需要对接 AI SDK 生态的宿主。不做 `fromUIMessage` 双向（parts 归并语义复杂、收益低）。

**（5）外部佐证。** Ant Design X 2.9 同样没有采用 UIMessage（自有 MessageInfo/SSEOutput），证明「组件库自有协议 + 可选适配」是可行路线；反例是 AI Elements 全组件直接消费 UIMessage——但它是「复制源码进 React 项目」的分发形态，与 npm 组件库的约束不同。

### 2.3 ToolCallInfo 状态机扩宽（本决策的具体化）

```ts
// core/src/types/index.ts（阶段 0 由集成者修改，非 dev 组）
export type ToolCallStatus =
  | 'pending'             // 排队/输入流式（AI SDK: input-streaming）
  | 'calling'             // 执行中（input-available 运行期）——旧值保留
  | 'awaiting-approval'   // 等待人工审批（approval-requested）
  | 'completed'           // 完成（output-available）——旧值保留
  | 'denied'              // 用户拒绝（output-denied）
  | 'error'               // 失败（output-error）——旧值保留

export interface ToolCallInfo {
  id: string
  name: string
  arguments: Record<string, unknown>
  result?: unknown
  error?: string
  status: ToolCallStatus   // 原 'calling'|'completed'|'error' 是新枚举子集
  duration?: number
}
```

**设计注记**：AI SDK 的 `approval-responded` 是瞬态（回应后立刻回 `calling`），UI 无需独立渲染态，不落枚举。旧三值语义不变，dev-server 与既有测试零改动即通过。

### 2.4 需总架构师拍板的三个子项

1. **`StreamChunk` 是否本期新增 `'source'` 型**（引用流式到达）。渲染组件（Sources/InlineCitation）只吃 `Message.sources`，不依赖流式通道；RAG 场景中 sources 也常随 tool_result（search_docs）或 done 帧返回。**建议：本期不加**，引用数据走 `Message.sources` + 宿主组装，`'source'` chunk 型列 P2——把阶段 0 对 useChat 消费链的波及降为零。
2. **审批回传通道**。ToolConfirmation 只 emit approve/reject 给宿主，本期不动 StreamChunk/adapter 协议（dev-server 演示用宿主 mock）。**建议：UI 先行、协议 P2**。
3. **BranchPicker 分支数据放哪**。A：`Message.metadata.branches?: string[]` 约定（零协议改动）；B：core 加显式可选字段。**建议：本期 A**，P2 视使用反馈升正式字段（对齐「别急加字段」评审纪律的反向应用：元数据逃生舱就是为这类探索期能力准备的）。
